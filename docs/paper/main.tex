\begin{abstract}
Open-weight text-to-SQL models return one query per question with no sign of whether it can be trusted. We reproduce the open CodeS-1B model, then make it say when it is unsure. On the 1,034 Spider development questions we measure 77.8\% execution accuracy against the paper's 77.9\%, using the authors' own evaluator. We execute the four candidate queries that beam search already produces, count how many return the same result, and abstain when that agreement is low. At 90.4\% coverage the system is right 83.3\% of the time instead of 77.8\%, and gives 156 wrong answers instead of 230; over ten calibration/test splits the gain over random abstention is $+5.46$ points (paired $t$-test $p=7.7\times10^{-10}$, Wilcoxon $p=9.8\times10^{-4}$, bootstrap 95\% CI $[+4.5,+6.7]$). Because an examiner noted that candidates are often copies, we measure how many are different (all four in 56\% of questions) and repeat the study over different queries only, with CodeS-3B, and with eight sampled candidates; the gain holds in each. The pipeline reaches 69.5\% on Spider-Realistic (paper: 70.9\%) and runs on a live PostgreSQL database through a read-only SQL translation, where 94.4\% of the Spider gold queries return the same rows as on SQLite. It ships as a desktop application that runs locally. Test-suite accuracy and a full BIRD evaluation are TBD.
\end{abstract}

\section{Introduction}
A natural-language interface to a database is only useful if its users can tell when to believe it. Text-to-SQL models are usually compared by how often they are right when they answer every question \cite{deng2022recent, hong2024nextgeneration}, but a wrong query is more costly than no query: it returns a plausible table that looks like an answer. The strongest systems rely on closed hosted models \cite{pourreza2023dinsql, gao2023texttosql, pourreza2024chasesql}, which means a company's schema is sent to a third party. CodeS \cite{li2024codes} narrows that gap with open models of 1B to 15B parameters, but like the others it returns one query with uniform apparent confidence.

This paper does three things.
\begin{enumerate}
\item \textbf{Reproduction.} We reproduce SFT CodeS-1B on Spider \cite{yu2018spider} within 0.1 points of the published figure, after auditing our harness line by line against the authors' code and fixing the errors that audit found (Section~\ref{sec:repro}).
\item \textbf{Confidence-aware abstention.} We use the candidates CodeS already generates: the system executes all of them, measures how many agree on a result, and declines to answer, with a clarifying choice, when agreement is low. We evaluate this as an accuracy--coverage trade-off with a pre-registered significance protocol (Section~\ref{sec:abstain}).
\item \textbf{Candidate diversity and other settings.} We test the claim behind the method --- that agreement among candidates carries information --- when the candidates are partly duplicates, with a larger model, with sampled candidates, on rewritten questions and on a live PostgreSQL server (Sections~\ref{sec:diversity}--\ref{sec:beyond}).
\end{enumerate}

All numbers below come from logged runs (seed 42, hardware and runtime recorded for each) and the scripts that analyse them; a number we did not measure is marked TBD.

\section{Related Work}
Spider \cite{yu2018spider} is the standard cross-domain benchmark, scored today by execution rather than by string match, with test-suite accuracy \cite{zhong2020semantic} as a stricter variant. Spider-Realistic \cite{deng2020structuregrounded}, Spider-Syn \cite{gan2021towards} and BIRD \cite{li2023can} probe robustness to wording, synonyms and large real-world databases. Methods moved from graph encoders \cite{wang2019ratsql, cao2021lgesql} and constrained decoding \cite{scholak2021picard} to large language models, prompted \cite{pourreza2023dinsql, gao2023texttosql, wang2023macsql, talaei2024chess} or fine-tuned \cite{li2024codes, li2023resdsql}. BRIDGE \cite{lin2020bridging}-style value matching, which CodeS keeps, adds matched cell values to the prompt.

Our abstention rule combines two older ideas: self-consistency, which trusts the answer that most sampled reasoning paths reach \cite{wang2022selfconsistency}, and selective classification, which lets a model decline inputs and reports the accuracy--coverage trade-off \cite{geifman2017selective}. Execution-guided repair, as in DIN-SQL \cite{pourreza2023dinsql}, addresses queries that fail; we measure it and find it addresses a small share of CodeS's errors (Section~\ref{sec:abstain}). To our reading of the surveys \cite{hong2024nextgeneration, liu2024a, mohammadjafari2024from, shi2024a, qin2022a}, none of the systems reviewed reports an accuracy--coverage curve for the generated query; the claim here is limited to those works.

\section{Reproducing CodeS}
\label{sec:repro}
\textbf{Pipeline.} For each question CodeS builds a prompt from the database: every table with its columns, types, keys and representative values, human-readable column descriptions, and stored values matched to words in the question by the authors' value retriever. The model generates four candidates by beam search and returns the first that SQLite accepts (\texttt{EXPLAIN QUERY PLAN}), otherwise the first beam. We use the authors' fine-tuned \texttt{seeklhy/codes-1b-spider}, fp16, one Tesla T4.

\textbf{Harness audit.} Our first runs scored 64.8--73.8\%. We compared the harness line by line with the authors' code and found a bug in our port (numbers were never matched by the value retriever, changing the prompt for 12.4\% of questions), missing column descriptions, and a simplified scoring metric that was not the paper's. We fixed these, switched to the official evaluator \cite{zhong2020semantic} (execution match), and kept the earlier runs in the log, marked as superseded.

\textbf{Result.} The corrected pipeline reaches 77.8\% execution accuracy (804/1034; run T2-005, re-run from scratch as T2-006 with an identical result), against 77.9\% in the paper. Table~\ref{tab:repro} shows the effect of each fix and of the model size. The 3B model reaches 81.8\% (paper: 83.4\%, $-1.6$ points). Test-suite accuracy was not computed (TBD).

\textbf{Ablation.} Removing one component at a time (official metric, same model and seed) lowers accuracy in every case: foreign keys $-0.9$ points, representative column values $-1.4$, candidate selection $-1.8$, value retriever $-1.9$. These differences are 9--20 questions each and were not tested for significance; the order of the two smallest effects should not be over-read. Accuracy falls with difficulty: 90.3\% on easy, 83.6\% medium, 64.9\% hard and 56.6\% extra-hard questions.

\textbf{Deviations.} We match values by scanning all distinct values rather than the authors' Lucene BM25 pre-filter; we do not apply the optional schema classifier; and we use newer PyTorch and transformers versions on one T4 instead of eight A800 GPUs.

\section{Confidence-Aware Abstention}
\label{sec:abstain}
\begin{figure*}[t]
\centering
\includegraphics[width=0.8\textwidth]{figures/final_pipeline.png}
\caption{System architecture: the reproduced CodeS components, the abstention step added here, and the application.}
\label{fig:pipeline}
\end{figure*}

\textbf{Method.} Of the 97.3\% of queries that execute, many still return the wrong rows, so repairing failures cannot fix most errors. Execution-guided repair, tried as in DIN-SQL, sent back 377 failed queries over 211 questions; 61 then ran and one more answer became correct (77.76\% $\to$ 77.85\%). We therefore turned to the queries that run but are wrong. All candidates are executed (read-only, on the original database); the \emph{agreement} $a$ of the returned answer is the share of candidates whose result equals it, and $0$ if the returned query fails. The confidence is $c=a+0.01\,p_b$, where $p_b$ is the softmax beam probability of the returned candidate (a tie-breaker only). The system abstains when $c<\tau$: it then shows no table, but lists the distinct results of the candidates as readings for the user to choose from. No model is retrained (Fig.~\ref{fig:pipeline}).

\textbf{Protocol.} Fixed before the results were seen: ten random 50/50 calibration/test splits of the 1,034 questions; $\tau$ chosen on the calibration half for at least 90\% coverage and applied to the test half; accuracy on answered questions compared with random abstention at the same coverage (the model's accuracy on that half); one-sided paired $t$-test and Wilcoxon signed-rank test at $\alpha=0.05$; and a question-level bootstrap (5,000 resamples) that does not rely on the splits being independent. The deployed threshold, $\tau=0.2526$, is the median over the ten calibration halves. In words: abstain when no candidate runs, or when only one of four supports the answer and its beam probability is below about 0.26.

\textbf{Results.} Table~\ref{tab:abstain} and Fig.~\ref{fig:curve} show the outcome. At 90.4\% coverage the system answers correctly 83.3\% of the time against 77.8\% for answering everything; wrong answers fall from 230 to 156 ($-32\%$). Of the 99 questions it declines, 74 would have been wrong and 25 correct. The mean gain over random abstention is $+5.46$ points (SD 0.71), positive in all ten splits: paired $t=24.4$, $p=7.7\times10^{-10}$; Wilcoxon $W=55$, $p=9.8\times10^{-4}$ (the smallest value possible with ten pairs); bootstrap 95\% CI $[+4.51,+6.71]$. We reject the null hypothesis of no gain. Beam probability alone gives a smaller gain ($+3.08$ points); agreement is higher than beam probability by 2.37 points on the same splits (paired $t=6.31$, $p=1.4\times10^{-4}$).

\textbf{Limits of the signal.} Agreement is not calibrated at the top: 11.7\% of answers on which all four candidates agree are still wrong. Over the whole curve, beam probability ranks answers slightly better (area under the risk--coverage curve 0.0905 against 0.1025 for agreement; random 0.2224, perfect ranking 0.0269); agreement is ahead from full coverage down to about 74\% coverage, the region where the operating point lies. Agreement takes only five values, so intermediate coverages rely on the beam-probability tie-breaker.

\section{Are the Candidates Really Different?}
\label{sec:diversity}
At the review of this work an examiner observed that, for some questions, only two of the four candidates were different queries, and asked why the number is four. This matters, because agreement among copies measures nothing. We re-executed every saved candidate of run T2-006.

\textbf{Duplicates.} The four beams are four different queries for only 577 of 1,034 questions (55.8\%); 42 questions have one distinct query, 190 two and 225 three. For CodeS-3B the counts are 57, 234, 249 and 494.

\textbf{Agreement over different queries.} We recomputed agreement (``v2'') counting each different query once and comparing results up to row and column order, which also corrects 68 questions where only the column order hid agreement. Over different queries, accuracy rises with the number that agree: 0 agree: 0.0\% (28 questions); 1: 71.7\% (244); 2: 78.7\% (367); 3: 83.1\% (207); 4: 89.4\% (188). The abstention gain is unchanged in kind: $+5.14$ points as a share ($p=1.7\times10^{-9}$) and $+5.66$ as a count ($p=4\times10^{-11}$), against $+5.46$ for the evaluated rule. The conclusion does not depend on duplicates.

\textbf{Another model.} For CodeS-3B the same analysis gives agreement $+3.18$ points ($p=2.9\times10^{-6}$; 89.7\% coverage, 85.2\% accuracy on answered) and, over different queries, $+3.88$ ($p=3.6\times10^{-7}$). Abstention helps the larger and the smaller model, by less for the larger one, which is already right more often.

\textbf{Sampled candidates.} We also drew eight candidates by sampling (temperature 0.8) instead of beams (run SM-008). Plain accuracy is 77.08\% (beams: 77.76\%); a correct query is among the eight for 881 questions (85.2\%) against 859 (83.1\%) among four beams. Majority vote over the eight reaches 77.66\%, whereas majority vote over four beams was worse than the first-executable rule (75.73\% against 77.76\%). Agreement abstention holds ($+5.57$ points, $p=1.7\times10^{-7}$, 82.5\% accuracy at 90.0\% coverage), and the 491 questions on which all eight agree are correct 93.5\% of the time.

\textbf{Why four?} Four is what CodeS's inference code returns and what our threshold was calibrated on. The application now lets the user choose 2--12 candidates, over-generating beams (or sampling at rising temperature until the queries differ) so that candidates are different queries wherever the model has more than one way to answer. This was done after the evaluation: the measured accuracy and threshold are for four beams, and other counts are uncalibrated. A run with eight beams printed 78.8\% accuracy before it failed while saving its results; it is being re-run, and no further number from it is reported (TBD).

\section{Beyond Spider}
\label{sec:beyond}
\textbf{Rewritten questions.} Spider questions often name the columns. On the 508 development questions that Spider-Realistic \cite{deng2020structuregrounded} rewrites without column names, the pipeline (run on an Apple M4) reaches 69.5\% (353/508) against the paper's 70.9\% ($-1.4$ points). On the original wording of the same 508 questions it reaches 72.8\% (370/508), so the wording costs 3.3 points (bootstrap 95\% CI $[0.8, 5.9]$; 31 questions right only in the original wording, 14 only in the realistic one; exact McNemar $p=0.016$). Agreement stays informative there: accuracy is 86.9\% when all four candidates agree and 47.1\% when one does, and the balanced setting lowers wrong answers from 155 to 102. A run on BIRD Mini-Dev \cite{li2023can} was stopped after 18 of 500 questions and is not reported (TBD).

\textbf{A live database.} CodeS writes SQLite. For a server database we translate each query with sqlglot, accept only one read-only statement, and run it in a read-only transaction with a timeout and a row limit; the schema and a value index are read once at connection time. We copied the 20 Spider development databases into PostgreSQL 14 and ran every gold query and every saved prediction on both engines. With the final rewrites (string literals, case-insensitive \texttt{LIKE}, aggregate grouping) 94.4\% of gold queries (976/1034) and 93.7\% of predictions that run on SQLite (943/1006) return the same rows on PostgreSQL, up from 67.0\% and 71.1\% for plain translation; most remaining mismatches are \texttt{ORDER BY}\ldots\texttt{LIMIT} queries with tied rows. End-to-end accuracy and calibration on PostgreSQL, and MySQL, are not measured (TBD); a qualitative run of twelve questions on one database matched the gold answer ten times.

\textbf{The application.} The system ships as a desktop application (macOS; a Windows build is configured but untested) that runs the same evaluated code, shows how many of the queries agree, executes and displays every candidate, offers the readings when it abstains, and runs fully on the local machine with open weights, so the schema is not sent to a third party. Its models, thresholds and candidate count are user settings; only CodeS-1B with four beams has measured accuracy.

\section{Limitations}
(1) One benchmark and, for the main result, one model; the threshold was calibrated on the same development set it is reported on, which the split protocol and bootstrap address but cannot remove. (2) The ten splits reuse the same 1,034 questions. (3) Agreement can be unanimous and wrong (11.7\%), and is a coarser ranking than beam probability across the whole curve. (4) The ablation differences are small and untested for significance. (5) Test-suite accuracy, BIRD, MySQL and end-to-end PostgreSQL accuracy are TBD, and the larger CodeS models were not run. (6) Candidate counts other than four, and models other than CodeS-1B, are uncalibrated.

\section{Conclusion and Future Work}
An open 1B-parameter text-to-SQL model can be reproduced to within 0.1 points of its published accuracy and made to decline the questions it is likely to get wrong: at 90.4\% coverage it is right 83.3\% of the time instead of 77.8\%, with a third fewer wrong answers, using only the candidates it already generates and no retraining. The result survives duplicated candidates, a larger model and sampled candidates, and the system works on rewritten questions and a live server database. Next steps are the results marked TBD, calibrating the threshold for other candidate counts, per-database adaptation, and role-based access when connected to a company database.
